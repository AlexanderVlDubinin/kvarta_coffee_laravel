### 🛠️ Архитектура и Стек

* **Backend:** PHP 8.4 / Laravel 13. Базовый каркас расширен строгим правилом `Model::shouldBeStrict()` в `AppServiceProvider`.
* **Database:** PostgreSQL. Использовал PostgreSQL для лендинга для изоляции веб-потоков от фоновых процессов (очередей Laravel) при интеграции с Telegram (предполагается по ТЗ). Это исключает блокировки БД, гарантирует 100% сохранность заявок при сбоях внешней сети и обеспечивает гибкость развертывания приложения в Docker.
* **Frontend:** HTML5, JavaScript (Vanilla JS), Tailwind CSS v4 (сборка через Vite).
* **Архитектурный паттерн:** Сервисный слой. Валидация вынесена в Form Request (`StoreLeadRequest`), а бизнес-логика и дедупликация инкапсулированы в `LeadService`.

### 🛡️ Ключевые технические решения (Выбор СУБД, защита и UX)

1. **Выбор СУБД (PostgreSQL):**
   В ТЗ предлагалось использовать плоские файлы или SQLite. Однако для коммерческого веб-приложения (даже масштаба локальной мастерской) этот подход имеет ограничения:
    * **Проблема параллелизма (Concurrency):** Файловые хранилища и SQLite блокируют всю базу данных на запись (механизм *database-level locking*). При одновременной отправке заявок несколькими пользователями это неизбежно приведет к ошибкам блокировки строк и потере лидов.
    * **Безопасность данных:** Интеграция с полноценной СУБД PostgreSQL обеспечивает строгую типизацию данных (например, использование точных типов для UTM-меток, ограничений по длине строк) и транзакционность (ACID), исключающую появление «битых» или частично записанных лидов.
    * **Масштабируемость:** Использование PostgreSQL позволяет при необходимости мгновенно подключить к проекту CRM-систему менеджера, аналитическую панель или Telegram-бота, работающих с единой базой данных в режиме реального времени.
2. **Решение проблемы Race Condition (PostgreSQL Advisory Locks):**
   Вместо стандартной конкурентной проверки `where()->first()` бэкенд оборачивает создание лида в транзакцию и запрашивает эксклюзивную рекомендательную блокировку уровня транзакции `pg_advisory_xact_lock` на основе числового ID нормализованного телефона. Это гарантирует 100% защиту от дублей при Double Click и параллельных веб-потоках.
3. **Rate Limiting и Сетевая безопасность:**
   На уровне маршрутов API подключено middleware `throttle:leads-signup`, ограничивающее частоту до 3 отправок в минуту с одного IP. По рекомендации ИИ реализована Honeypot-ловушка (`mid_name`) для ботов — автоматический сброс спам-запросов без нагрузки на СУБД. Все вводимые клиентами строки санитаризируются через `strip_tags` (рекомендация ИИ).
4. **Бесшовная интеграция без Корзины:**
   По ТЗ корзина запрещена. Был разработан реактивный фронтенд-конструктор. При клике на карточки товаров JavaScript генерирует состав заказа налету, считает цену и агрегирует технические данные в скрытое поле `product`, оставляя поле `comment` для вопросов или личных пожеланий клиента.
5. **Умный интерфейс ошибок (UX):**
   Любое изменение состояния формы (ввод текста, выбор селекта, клик по кнопкам добавления товара) мгновенно и динамически скрывает как локальные ошибки валидации полей, так и глобальные плашки статуса заказа, обеспечивая чистый интерфейс. ИИ этого не учел при генерации кода формы. Недостаток обнаружен и исправлен при тестировании.
6. **Сбор Маркетинговых данных:**
   Скрипт автоматически парсит UTM-метки из URL браузера, вытаскивает `document.referrer` и сохраняет полную аналитику в базу данных для менеджера.

### 🤖 Опыт управления ИИ (Лог сессии)

**В процессе работы ИИ использовался:**
- как интерактивный соавтор для генерации текстов от лица основателей Ани и Дмитрия, для описания предлагаемых сортов кофе, а также для быстрой рутинной верстки кастомных селекторов на Tailwind CSS v4.
- для генерации регулярного выражения для валидации корректного белорусского телефонного номера.
- для создания блокировки уровня транзакции `pg_advisory_xact_lock` (первоначально мной была сделана стандартная проверка `where()->first()`).

**Где ИИ ошибся и как это было замечено:**
- ИИ допустил ошибку при валидации корректного белорусского номера телефона: предложенное регулярное выражение проверяло код оператора по наличию двух цифр ( \d{2} ), что может быть некорректно для белорусских операторов. Ошибка была замечена при изучении предложенного ИИ выражения и исправлена вручную (вариант, предложенный ИИ, оставлен закомментированным в файле `app/Http/Requests/StoreLeadRequest.php` как пример).
- При проектировании обработчика `fetch` (отправка заявки), ИИ допустил логическую ошибку в последовательности выполнения JS-команд: функция сброса интерфейса `handleInterestChange()` вызывалась после удаления класса `hidden` у плашки успеха. В результате плашка очищалась в памяти, но мгновенно скрывалась обратно. Ошибка была локализована при тестах через `console.log()` и исправлена изменением порядка вызова функций.
- При сборе UTM-меток - ИИ изначально предложил код, который собирал метки в момент клика по кнопке «Отправить». Но если покупатель до того перешёл по внутренней якорной ссылке лендинга, адресная строка браузера могла измениться, и window.location.search со всеми UTM-метками очистился. Я отловил это когда разбирался с UTM-метками вообще и изучал предложенный код. Я дополнительно проконсультировался с ИИ в другом чате, где и было предложено решение - перехватывать метки в момент первой загрузки страницы на стороне клиента (через JavaScript) и сохранять в сессию или локальное хранилище (localStorage).
